# gmxFlow Edge Cases Documentation

This document catalogs known edge cases encountered during gmxFlow pipeline execution and their solutions.

---

## Edge Case 1: Force Field Mismatch (Protein vs Ligand)

### Description
System crashes during NVT/NPT with segfaults or LinCS warnings at step 0, or NaN forces on GPU.

### Root Cause
- Protein generated with GROMOS53a6 force field (gmx pdb2gmx default)
- Ligand from LigParGen uses OPLS atom types
- Two different force field parameter sets cause incompatible interactions

### Symptoms
```
LINCS WARNING: bonds rotated more than 30 degrees
Assertion `isfinite(static_cast<float>(arg.x))` failed (GPU)
Segmentation fault at step 0
```

### Solution: Use Matching Force Field
Key insight: **Both protein AND ligand must use the same force field.**

```bash
# Option A: Use OPLS-AA for protein (matches OPLS ligand from LigParGen)
gmx pdb2gmx -f protein.pdb -o protein.gro -ff oplsaa -ignh -water tip4p

# Option B: Generate GROMOS-compatible ligand parameters
# Use GROMOS GAFF or reparameterize ligand with GROMOS types
```

### When This Applies
- Any protein-ligand simulation
- Always verify protein.ff == ligand.ff
- LigParGen generates OPLS → use OPLS for protein

## Edge Case 2: Empty [ pairs ] Section in Ligand Topology

### Description
Energy minimization (Step 5) fails with 100+ warnings: "No default LJ-14 types for interaction '1 4 1'"

### Root Cause
- Ligand topology file (`ligand.itp`) generated by LigParGen contains an empty `[ pairs ]` section
- System uses GROMOS53a6 force field for protein, but ligand uses OPLS atom types
- GROMOS force field has `gen_pairs = no` by default (does not auto-generate 1-4 interactions)
- Empty `[ pairs ]` section triggers "Too few parameters" warnings

### Symptoms
```
gmx grompp -maxwarn 1 ... 
WARNING: Too few parameters for LJ-14 interaction type 1 4 1 (142)
[ ... 100+ similar warnings ... ]
ERROR: Cannot use -maxwarn 1 with 105 warnings
```

### Workaround Used
```bash
# Run grompp with -maxwarn 200 to suppress warnings
gmx grompp -f minim.mdp -c complex_solv.gro -p topol.top -o em.tpr -maxwarn 200
```

### Permanent Fix Applied
Removed the empty `[ pairs ]` section from `ligand.itp`:
- This allows GROMOS force field's default `gen_pairs` to auto-generate 1-4 interactions from combining rules
- Much cleaner solution than adding explicit pairtypes

### Recommended Auto-Handling
Add pre-processing in gmxflow.py before Step 5:
1. Check if ligand.itp exists
2. Remove any empty `[ pairs ]` section before running grompp
3. Or increase `-maxwarn` specifically for EM step when ligand is present

## Edge Case 4: Net Charge Warning with Ewald Electrostatics

### Description
System has non-zero total charge, triggering warning for Ewald electrostatics

### Warning Message
```
System has non-zero total charge: 1.999600
To use exact Ewald sum and PME, the system should be neutralized
```

### Root Cause
Ligand has +2 charge, system not neutralized with counterions

### Impact
- Warning only - EM still completes
- But proper Ewald electrostatics require neutral system

### Recommended Fix
Add counterion neutralization step before EM in ligand mode

## Edge Case 5: Pipeline Hardcoded -maxwarn Flag

### Description
All grompp commands in config.py hardcode `-maxwarn 1`

### Affected Steps
- Step 5 (EM)
- Step 6 (NVT)
- Step 7 (NPT)
- Step 8 (MD)
- Also in protein-only mode steps

### Issue
When warnings occur (even non-fatal), `-maxwarn 1` causes grompp to fail

### Recommended Fix
- Option A: Increase to `-maxwarn 5` for more flexibility
- Option B: Add logic to auto-detect and increase `-maxwarn` when ligand present
- Option C: Handle specific warning types individually

## Edge Case 6: GPU NaN / Infinite Forces

### Description
GPU simulation crashes with assertion failures for non-finite values.

### Warning Message
```
Assertion `isfinite(static_cast<float>(arg.x))` failed
cudaErrorAssert: device-side assert triggered
```

### Root Cause
- Unstable system (bad contacts, poor EM, or force field mismatch)
- With FEP/water model issues

### Solution
1. **Check EM quality** - rerun EM with stricter convergence (emtol = 100)
2. **Use CPU first** to test stability: `gmx mdrun -nb cpu`
3. **Verify force fields** match (Edge Case 1)

## Edge Case 7: Water Model Compatibility

### Description
grompp fails with "No such moleculetype SOL" or water parameter errors.

### Root Cause
- Water model (TIP4P/SPC/TIP3P) not included in topology
- Force field doesn't auto-include water model

### Solution
Ensure water model is included in topology BEFORE gmx solvate:

```bash
# For TIP4P - include before ligand!
#include "oplsaa.ff/tip4p.itp"
#include "ligand.itp"

# For SPC (default)
#include "oplsaa.ff/forcefield.itp"  # usually auto-includes
```

### When Applying
- Using TIP4P, TIP5P, or other explicit water models
- Always add water includes BEFORE ligand.itp if ligand has atomtypes

## Edge Case 8: NVT/NPT Coordinate Continuity

### Description
NVT completes but NPT fails - no nvt.gro or checkpoint available.

### Root Cause
- mdrun didn't write output coordinates (only trajectory)
- Using trajectory file (.trr) but need .gro for next step

### Solution
```bash
# Option 1: Use TPR checkpoint
gmx grompp -f npt.mdp -c nvt.gro -r nvt.gro -t nvt.cpt -o npt.tpr

# Option 2: Extract from trajectory (if no checkpoint)
gmx trjconv -f nvt.trr -s nvt.tpr -o nvt.gro -b 70 -e 100
# Select group 0 (System)
```

## General Recommendations

1. **Always match force fields** - protein.ff == ligand.ff
2. **Pre-flight Validation** - check EM quality before NVT
3. **Flexible Warning Handling** - use `-maxwarn 10` for grompp
4. **Ligand Topology Sanitization** - remove empty [ pairs ] sections
5. **Neutralization Check** - verify system charge before Ewald steps
6. **Test on CPU first** - confirm system stable before GPU
7. **Checkpoint files** - use `-cpt` for backup continuity
